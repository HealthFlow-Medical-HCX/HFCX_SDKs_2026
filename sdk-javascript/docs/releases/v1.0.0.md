## Highlights

- Full HFCX protocol support: registry lookup → JWE encryption (hard-
  pinned RSA-OAEP-256 + A256GCM) → Keycloak bearer auth → POST to the
  gateway, with retry/backoff and typed-error mapping. Async-only,
  per JS convention.
- Recipient-side pipeline with four independently toggleable
  validation layers (Bearer / Headers / Fhir / Egyptian), shipped via
  `RecipientHandler`.
- 27-entry `ErrorCode` catalog with a typed error subclass per code —
  wire-format-identical to the Java + Python + .NET SDKs.
- 27 Egyptian governorates as a first-class `EgyptianGovernorate`
  object.
- Reference recipient app under `docs/examples/recipient-fastify/`
  showing how to host `RecipientHandler` behind Fastify 5.
- Correlation-ID propagation via Node's `AsyncLocalStorage` that
  survives `await` boundaries; cross-SDK MDC key `correlation_id`
  matches Java + Python + .NET.

## npm install

```bash
npm install @healthflow/hfcx-sdk
```

The package is published as `@healthflow/hfcx-sdk` under the
HealthFlow-Medical-HCX npm organisation. ESM-only, Node 20+. Compile-
time dependencies: `jose` + `lru-cache`. No optional accelerators
required for any code path.

## Known gaps and follow-ups

- HAPI-equivalent full-IG profile validation is deferred. The
  hand-rolled `FhirValidator` enforces the same Egyptian-IG profile
  rules the other three SDKs do; swapping to a full-IG validator
  over a bundled `egyptian-ig.tgz` does not change the public
  `FhirValidator` surface.
- A reference JWKS-backed `BearerTokenValidator` is not bundled; this
  is intentional, so participants make a deliberate choice. A
  reference implementation can ship in a follow-up minor release.
- Browser-targeted bundling has not been fully smoke-tested. The
  package is pure ESM and should bundle through Vite / Rollup /
  esbuild without modification, but a few internals (the registry
  client's `node:crypto` `X509Certificate` parser) require Node APIs
  and would need polyfills for browser use.

## Acknowledgements

Behaviour was ported from the Java, Python, and .NET SDKs'
implementations rather than rewritten from the platform spec — the
protocol primitives, the 27-entry error catalog, and the four-layer
recipient pipeline are byte-for-byte cross-SDK invariant. Cross-SDK
round-trip fixtures under `tests/fixtures/cross-sdk/` close the loop
with all three sister SDKs.
